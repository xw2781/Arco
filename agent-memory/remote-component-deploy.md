Since 2026-08-17, component rebuilds go through `python server-components/deploy.py` (no arguments = every stale component). It queues a request under `E:\ArcRho Server\requests\builds` and the **ArcRho Build Listener** — the "Listen for build requests" toggle in `server-components\build_manager.bat` on the server — runs the same `build_exe.py` locally, streaming its log back. Exit codes: `0` ok, `1` build failed, `2` usage/precondition, `3` no listener running (relay the CLI's message asking a human to start it; nothing else in the flow needs a person).

**Why:** a deploy from a client is dominated by writing the frozen build across the share. Measured 2026-08-17 on this Client PC: the same share **reads at 50 MB/s but the deploy's writes ran at 0.18 MB/s**, so ~5 of each ~6-minute deploy was transfer, not build. Metadata is not the problem — enumerating all 1,667 deployed files took 1.2 s (0.7 ms/file). Do not re-derive this; measure only if the numbers stop matching.

**How to apply:** never hand-pick which components to rebuild — `deploy.py` derives staleness from each component's bundled source roots, and `arcrho_build_components.py` is now the single owner of that rule for both the GUI and the CLI. An `frontend/app_server/` edit makes Bridge, Engine **and** Gateway stale; picking by memory already caused a missed Gateway deploy. Uncommitted work deploys fine: the request carries a patch of the affected trees against the newest commit the server can resolve, plus untracked files, so there is no reason to commit or push just to deploy.

Gotchas: the listener **resets its own clone** on every request, so nothing may be edited there, and it should be restarted after a change to its own modules (its heartbeat reports the commit it started from). Anyone who can write the queue folder can run repository code on the server — the guards are the share ACLs plus the listener's optional user allowlist.

**Check which clone the listener is resetting before trusting any deploy.** `REPOSITORY_ROOT` is derived from where the listener's *own code* lives, so it is whichever clone `build_manager.bat` was started from, on whatever machine started it — and there is **no guard against that being the clone you are working in**. A deploy runs `checkout --force --detach` + `reset --hard` + `clean -fd` over that tree, detaching HEAD and destroying every uncommitted change outside the affected component roots. This is not `--ref`-specific: working-tree mode runs the same three commands and only restores the affected roots from the patch afterwards. Read `Repository` in `E:\ArcRho Server\runtime\instances\arcrho_build_listener\*.json` before deploying. `discover_fresh_listener_heartbeats()` treats anything older than 60 s as dead.

**Since 2026-08-23 it has its own clone: `E:\XWSpace\Repos\ArcRho-buildbot`.** It had been running from the working clone `E:\XWSpace\Repos\ArcRho`, and a deploy during the persisted-JSON v4 conversion did exactly the damage above — reverted an uncommitted `docs/general_prompts.md` edit and deleted the untracked tool scripts. The buildbot clone carries the working clone as a `worktree` remote, so `git fetch --all` resolves a commit that has not been pushed and deploys still need no push. `tools/arcrho_service_control.ps1 -Action listener-stop` / `listener-start` moves it; the payload only carries build-relevant files, so anything outside those roots is reset away, not patched back.

**A force-stopped component blocks the next Engine deploy.** `build_exe.py` waits on the heartbeat files under `E:\ArcRho Server\runtime\instances\<component>\` to decide the old Engine is gone, and a process killed rather than closed leaves its file behind — so the wait cannot succeed, times out at 180 s and aborts with "The live ArcRho Engine did not stop within 180s (N heartbeat(s) still present)". Clear them with `tools/arcrho_service_control.ps1 -Action clear-stale-heartbeats`, which only removes a heartbeat with no live process behind it.

**On the Server PC the CLI starts the listener itself (2026-10-30).** With no fresh heartbeat and the workspace drive local, `deploy.py` launches `build_manager.bat` from the one sibling clone carrying `.git/arcrho-build-clone`; the Manager auto-listens there (see [[server-components-folder-rename]]) and the CLI waits up to 90 s for its heartbeat. Only a Client PC, or a Server PC without exactly one marked clone, still gets exit `3`. Elsewhere, starting `build_manager.bat` leaves the checkbox off. The listener feature cannot deploy itself: a server clone predating it shows a manager window with no such checkbox at all, so the first hop is manual (push, then `git pull` in the server clone, then restart the manager).

**One component's failure kills the whole request.** `_run_components` stops at the first non-zero exit ("a failure usually means the sources are broken"), and components run in the CLI's order, so a single failure on an early component silently skips every later one. On 2026-08-17 a swap lock on `admin` cost bridge/engine/launcher/orchestrator/gateway their build in a no-argument deploy. If a run reports one error, assume nothing after it was built and re-check `--stale`.

**"The working-tree patch did not apply to the base commit" with only some hunks failing is a listener bug, not your patch.** Until 2026-08-17 `arcrho_build_listener._apply_patch` piped the patch to `git apply` through a text-mode `subprocess.run(text=True)`, which on Windows rewrites every `\n` as `\r\n`; against the server clone's LF files git then rejects hunks anchored at a file's start or end (a docstring rewrite on line 1, removing a file's last line) while the rest apply. The fix (send `patch_text.encode()` in binary mode; regression test `test_the_patch_reaches_git_byte_for_byte_on_an_lf_clone`) is in the working tree/main, but the running listener keeps its old code until someone pushes, pulls in `E:\XWSpace\Repos\ArcRho`, and restarts `build_manager.bat` on the server — check the heartbeat's `Commit` before assuming it is fixed. Until then the fallback is each component's `build_exe.py` from the client (slow, works). Still unfixed on 2026-08-18: the listener heartbeat reported `Commit 22838d99`, one commit before the fix `ccf75de`, and a Bridge deploy failed with the whole patch rejected at `main.py:41`. `ARCRHO_DEPLOY_ROOT="E:\ArcRho Server" python server-components/src/arcrho_bridge/build_exe.py` then built and deployed it from the Client PC in about 8 minutes, and the server's Orchestrator relaunched the Bridge and its ResQ worker on its own. Resolved by 2026-08-20: the listener on `NE7SASWPN02` reported `Commit e41cc0fa`, which contains `ccf75de`, and a bridge+engine+gateway deploy succeeded.

**`corrupt patch at <stdin>:<n>` is a different bug from `patch does not apply`, and it was in `deploy.py`, not the listener.** `_git()` ended in `return completed.stdout.strip()`, and every caller shared it -- including the `git diff --binary` that becomes the payload. A hunk whose trailing context is a blank line ends in a line containing one space; `strip()` deleted it, so the final hunk was one line shorter than its own header claimed and `git apply` refused the *whole* patch, naming the patch's last line. It only bites when the last hunk of the whole diff ends on a blank line, which is why deploys worked for months. Fixed 2026-08-20: `_git(..., strip=False)` for the diff, and the payload no longer appends a newline git already wrote. Regression test `test_a_patch_ending_on_a_blank_context_line_survives_the_payload` in `server-components/tests/test_build_request_protocol.py` -- it fails on the old code, so check `strip=False` is still on that call before blaming the listener. Unlike the CRLF bug this one lives in the client CLI, so the fix applies immediately with no listener restart.

**A queued request can fail once with `[Errno 13] Permission denied` on the listener's own request JSON.** Seen 2026-08-18 on the first of two back-to-back deploys; the immediate retry queued a new request and the listener claimed it normally, so treat a single Errno 13 as transient and retry once before concluding anything about ACLs.

**A working-tree deploy ships everyone's edits**, not just yours: this clone is worked in by more than one session at a time (seen 2026-08-17, an in-flight SQL Server/Arcode feature under `frontend/app_server` while an unrelated task was finishing). The CLI prints the changed and new files for that reason — read the list, and if it contains work that is not yours, stop rather than deploying it. `--stale` reads the same shared tree, so it can report components stale because of somebody else's work in progress.

**The patch is snapshotted when `deploy.py` starts.** An edit made while a deploy is running is not in it, even for a component that has not started building yet — on 2026-08-19 a Bridge source change written 37 s after launching a no-argument deploy was absent from the Bridge that deploy produced, while `--stale` afterwards reported bridge as `Updated` because staleness compares the deployed build's timestamp against source mtimes. Finish editing before deploying, or deploy that component again.

**A `WinError 5` renaming the build status JSON aborts the rest of the run while the finished components stay deployed.** Seen 2026-08-19: renaming the status file .build-*.json.<hex>.tmp to build-*.json under the requests/builds/statuses folder failed as Access denied, the CLI printed `Build failed:` and `[error]` and still exited **0**, Engine and Bridge were deployed and verified, and Gateway — the component the task actually needed — was never built. Do not read exit 0 as success when the log contains `[error]`; re-check `--stale` and deploy what remains, one component per run if it recurs.

**On this Client PC the auto-mode permission classifier blocks `deploy.py` runs** (even `--stale`), so `.claude/settings.local.json` carries allow rules for `Bash(py -3.10 server-components/deploy.py*)` / `Bash(python server-components/deploy.py*)` and their `PowerShell(...)` twins (added 2026-08-20 with user approval). Rules are prefix-matched, so run the bare command — a `Set-Location ...;` prefix breaks the match and re-triggers the classifier.

**The working-tree payload is scoped to the component source roots, so "another session is editing" is not on its own a reason to stop.** `_repository_relative_roots()` limits the `git diff` to each component's bundled trees, and `_base_commit()` diffs from the merge base with the remote so local unpushed commits ride along too. On 2026-08-31 a bridge+engine+gateway deploy ran cleanly from this tree while another session held uncommitted edits under `frontend/ui/method_pages/dfm/` -- `frontend/ui` is in no component's roots (only `frontend/app_server` is), so those files were never in the payload. Preview it instead of guessing: import `deploy` and print `git diff --name-only <base> -- <roots>` plus `git ls-files --others --exclude-standard -- <roots>`. Deploy by ref only when the *scoped* list actually contains someone else's work.

**When the tree holds another session's in-flight work, commit yours and deploy by ref.** `py -3.10 server-components/deploy.py --ref <sha> bridge engine gateway` builds exactly that commit; the buildbot clone resolves an unpushed commit through its `worktree` remote, so no push is needed (done 2026-08-27 with `7a3639fd`, request `build-260827-183621`). A working-tree deploy would have shipped the other session's uncommitted propagation edits. The CLI's stdout stays empty until the run ends; follow progress in `E:\ArcRho Server\requests\builds\statuses\<request>.json` and `logs\<request>.log`.

Bridge (+ worker), Engine (3 instances), and Gateway all came back on their own within 20 s.

Known roles: admin, bridge, engine, gateway, launcher, orchestrator.` — the request is rejected before anything builds, and the CLI exits 1. Name the components it knows (`deploy.py bridge engine gateway`, 7 minutes for all three) and report that `credential` stays undeployed until someone restarts the listener from a checkout that carries the role.
