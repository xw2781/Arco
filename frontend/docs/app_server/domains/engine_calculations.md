# App Server Domain: Engine Calculations (Server-Hosted Transport)

## Purpose
<!-- MANUAL:BEGIN -->
Run the legacy Arco Engine calculation exchange — publish one `request-*.json` into the workspace `requests` root and wait for the CSV the Engine writes — and the whole dataset run built around it on the ArcRho Server host over HTTP instead of over the mapped drive. This is a transport around the unchanged `ArcoTri` / `ArcoVec` / `ArcoHeaders` file contract and the unchanged `arcrho_runtime_service` routes: the Engine still claims the same request file and writes the same CSV to the same location, and the cache validation, sidecar write, dependent enqueue, and index refresh are the same service code; only the process that runs them moves from the Client PC to the machine-wide Arco Gateway, where every step is a local-disk operation.
<!-- MANUAL:END -->

## Entry Points
<!-- MANUAL:BEGIN -->
No new browser-facing route. Four operations share one Gateway route:

| Operation | Client entry | Service run on the host |
| --- | --- | --- |
| `dataset_run` | `POST /arcrho/tri`, `/arcrho/tri/refresh`, `/arcrho/vec`, `/arcrho/vec/refresh` via `engine_calculation_service.run_hosted_dataset_operation` | `arcrho_runtime_service.run_arcrho_tri` (options `force_refresh`, `local_only`, `allow_derived`, `write_sidecar`, `temporary_session_id`) |
| `dataset_precheck` | `POST /arcrho/tri/precheck`, `/arcrho/vec/precheck` via the same client function | `arcrho_runtime_service.arcrho_precheck` (options `local_only`, `allow_derived`, `temporary_session_id`, `allow_runtime_cache_provenance`) |
| `dataset_csv` | Excel add-in formula-entry loads and explicit refresh over the signed Gateway route | `excel_dataset_service.read_dataset_csv` for triangles/vectors; existing header/settings readers for project-level functions. No `force_refresh` option. |
| `exchange` | every remaining `arcrho_runtime_service` request site that runs in a client process — dataset label hydration in a local dataset load, Result Selection source loads, calculated-dataset input materialization, and the exchanges inside a run that itself executes locally — via `engine_calculation_service.run_engine_calculation(pairs, data_path, timeout_sec)`, which returns `ok`, `status` (`completed` / `timeout` / `gateway_error`), `request_file`, `transport`, an optional `message`, and on a hosted success `csv_text`, the CSV's exact text | `engine_calculation_service.publish_and_wait`, then the CSV's text |

The period headings are not an exchange from the client any more: `POST /arcrho/headers` is the Gateway-required `arcrho_headers` workspace read (`arcrho_runtime_service.get_project_headers`), so the settings check, the cache lookup and any Engine run happen on the server host and the labels come back in the reply. `POST /arcrho/headers/cache/clear` is the Gateway-required `arcrho_headers_cache_clear` workspace mutation (`clear_arcrho_headers_cache`, idempotent: a repeat finds the files gone).

Gateway side: `POST /api/engine-calculations` (`arcrho_engine_calculation_contract.ENGINE_CALCULATION_PATH`), authenticated with the same per-user HMAC headers as hosted saves and workspace reads. `GET /api/capabilities` advertises `engine_calculation_functions` and `engine_calculation_operations`; a client facing an older gateway that lists only `exchange` keeps the dataset routes local.
<!-- MANUAL:END -->

## Key Files
<!-- MANUAL:BEGIN -->
- `python-api/src/arcrho_engine_calculation_contract.py` - The canonical `ENGINE_CALCULATION_KINDS` registry (Engine function → exact request-file keys the Engine reads, whether a reserving class is named, allowed output variants and operations), the `OPERATION_OPTIONS` table (each operation's option names and types), server-owned keys a client may never send (`DataPath`, `StatusPath`, `RequestId`, `UserName`), request validation, wait clamping, route path, and the exchange response shape.
- `app_server/helpers.py` - `build_engine_request_info` (the `key = value#...` request line), `send_request_like_vba` (publishes into `config.REQUEST_DIR` and stamps the acting user), `wait_for_file` (local file-event wait, or probe-and-poll on a network drive), `is_network_path`.
- `app_server/services/engine_calculation_service.py` - `publish_and_wait` (the exchange itself, identical on both hosts), `execute_hosted_engine_calculation` (the server-side entry: derives the output path with `set_data_path_like_vba` — or the Temporary view path for `OutputVariant: temporary_view` — then publishes and waits, or delegates a dataset operation to `arcrho_runtime_service`), `run_engine_calculation` (client transport for one exchange: capability probe, request signing, the result text from the reply, diagnostics record), and `run_hosted_dataset_operation` (client transport for a dataset run/precheck: same selection, response returned verbatim with rebased paths, dataset handle registration, `504` after acceptance).
- `app_server/api/arcrho_router.py` - The `/arcrho/tri*` and `/arcrho/vec*` routes build the pairs and options once and hand them to `run_hosted_dataset_operation` with the local service call a server process runs; the output path is resolved only inside that local call, because resolving it looks the project folder up on the workspace drive. The headings and their cache clear go through the workspace read and mutation clients.
- `app_server/services/workspace_read_client.py` - `post_signed_json`, `GatewayTransportFailure`, `cached_gateway_capabilities`, and `rebase_workspace_paths`, shared with workspace reads.
- `server-components/src/arcrho_gateway/engine_calculations.py` - Server-side executor: authenticates, validates against the contract, imports the canonical executor named by `EXECUTOR_MODULE` / `EXECUTOR_FUNCTION`, runs it under `acting_identity`, and maps a service `HTTPException` to the same status.
- `server-components/src/arcrho_gateway/main.py` - Route dispatch (shared with workspace reads) and the capability field.
- `server-components/src/arcrho_gateway/build_exe.py` - Bundles the contract, the executor module, and `watchdog` so the server-side wait is a file-system event.
<!-- MANUAL:END -->

## Data/State/Caches
<!-- MANUAL:BEGIN -->
- Excel 3.0.1 stores results in each workbook and makes no data requests during open or ordinary recalculation. Formula entry loads missing requests and commits them to the snapshot after calculation; explicit refresh also fetches requests already saved. Both paths serve every sidecar-backed dataset from the sidecar's declared published CSV whenever it can provide the requested shape. Manual/input and Engine-generated values support the canonical coarser-period rollup in memory; Engine periods come from the published CSV, not its source-table granularity. An Engine-generated dataset at any other shape or mode is built by the Engine as a technical cache beside the publication, like a sidecar-less request, leaving the publication untouched. Manual/input, calculated, and method outputs at an unsupported shape fail without touching stored figures. Sidecar-less generated requests reuse current technical provenance or generate a new temporary result, and temporary formulas read dependencies under the same ownership policy. A request is refused while propagation holds the class. Frontend dataset-run, precheck, and numeric-formula behavior remain unchanged.
- Transport selection, per request, as for workspace reads: where the workspace root sits does not matter (a Client PC whose root is on its own disk, such as the local test server, still asks its Gateway), the process must not run with `ARCRHO_RUNTIME_SERVER_ROOT` set (Engine, Bridge, Gateway publish locally), and the selection is `require_client_gateway`: a Client PC always sends the calculation to its Gateway and is refused, never served by a local request file, when it is not signed in (`401`), when the Gateway does not answer or does not list the Engine function and operation (`503`), or when the request does not validate against the contract (`400`, `request_not_hostable`). Only a server process runs `publish_and_wait` (or the hosting Engine's in-process calculator) itself.
- Request: only the legacy request-file keys travel, as ordered `[key, value]` string pairs (order is part of the request — the header cache file name is derived from pair values in order), plus `TimeoutSeconds` (clamped to 0.1–300 s; for a dataset run this is the per-exchange Engine budget, `config.ENGINE_REQUEST_TIMEOUT_SEC`), `Operation` (`exchange` by default), its `Options` (validated against `OPERATION_OPTIONS`: booleans, and a UUID-or-null `temporary_session_id`), an optional `OutputVariant` for the exchange (`canonical` or, for dataset functions, `temporary_view`), and the enrolled `UserName` with an empty display name (the server resolves the signed login's, so the client does not read the username index over the share). The server derives `DataPath` itself and stamps `UserName` from the acting identity, so a client can neither name an arbitrary output file nor act as another user. Key spellings are exact (`periodType`), because the Engine reads keys verbatim.
- Exchange response: `ok`, `status` (`completed` / `timeout`), the server's `data_path` and `request_file`, `wait_ms`, and on success `csv_text`, the exact text of the CSV the Engine wrote (read with its own line endings). The client rebases the server paths onto its own root, refuses (500) a `data_path` that differs from the one it computed, and hands `csv_text` to its caller: it never waits for the CSV on its own drive or reads it there. A success without the text (a Gateway older than this contract) is a `gateway_error` saying the server needs updating, not a drive read. A caller that parses the text as a dataset uses `helpers.read_dataset_csv_text`, which reads it exactly as `read_dataset_csv` reads the file, blank origins included.
- Dataset run / precheck response: the service's own response, verbatim (`ok`, `status`, `need_request`, `ds_id`, `data_path`, `request_file`, `calculated_updates`, `sidecar_written`, …), with every server-rooted path rebased onto the client's root. A successful `dataset_run` registers `ds_id` → rebased `data_path` locally through `dataset_service.register_dataset_handle`, exactly as the local route registers it, so the id-addressed `GET /dataset/{id}` and grid routes keep resolving. On the server the run executes with the Temporary view, sidecar, dependent-propagation enqueue, index refresh, and lock semantics unchanged; the exchanges inside it are local because the run is a server process.
- Failure rule: a gateway-layer failure before the request could have been acted on is the user's error from `failure_error` (a refused signature asks the user to sign in again). Once the request may have been accepted — a timeout waiting for the answer, a dropped connection or invalid body after the server answered — an exchange reports `timeout` / `gateway_error` with `message`, and a dataset operation raises `504` (`Reload the dataset before retrying`); neither is retried, because a second request makes the Engine compute the same CSV twice and a second run would repeat the sidecar and dependent work. A refusal raised by the hosted service itself (a project the server cannot find, `423` on a locked cache, `422` on a bad session id) passes through as the same `HTTPException`.
- No receipt: a calculation is a deterministic function of the workspace, so the transport keeps no idempotency receipt; the caller's own retry is a fresh request.
- Identity: `send_request_like_vba` stamps `UserName` from `user_identity_service.get_windows_login_name()`, which answers with the acting identity when the Gateway publishes on a user's behalf; the sidecar the client writes afterwards still carries that user's display name.
- Diagnostics: one record per request in `client_read_latency.jsonl` with `read_kind: engine_calculation`, `engine_function`, `operation` (dataset operations), `transport` (`http_gateway` or `smb`), `reason` (`server_process` for a run in place; on a Client PC the refusal: `gateway_disabled`, `gateway_config_invalid`, `gateway_unreachable`, `kind_not_advertised` for a function or operation the Gateway does not list, `request_not_hostable`, `gateway_rejected:<code>`), `outcome`, `total_ms`, `remote_ms`, `server_wait_ms` (exchange), `http_status`, and the logical project/class/object names — never payload data.
<!-- MANUAL:END -->

## Common Change Tasks
<!-- MANUAL:BEGIN -->
1. Host another Engine function: add one `EngineCalculationKind` entry naming the exact request-file keys its handler reads; the Gateway advertises it on the next deploy and the client routes it the moment the capability appears. Keep `set_data_path_like_vba` able to derive its output path.
2. A request site that targets a different output location than the canonical cache must name it as an `OutputVariant` the contract knows and `resolve_engine_output_path` can derive; the client never sends a path.
3. Host another route: add an operation and its option table to the contract, dispatch it in `execute_hosted_engine_calculation` to the canonical service function, and wrap the route in `run_hosted_dataset_operation` with the local call a server process runs; the Gateway advertises the operation on the next deploy.
4. Rebuild and redeploy the Gateway after any change here; the Engine and Bridge bundle `app_server` too and follow their own deployment rules.
<!-- MANUAL:END -->

## Known Risks
<!-- MANUAL:BEGIN -->
- When source dates cannot be assigned to a development period, the Engine reports date-setting guidance through the existing calculation error message. If source development extends beyond Development End Date, the message names both months and directs the user to Project Settings > General Settings, followed by a data refresh. Calculation and transport contracts are unchanged.
- Each hosted calculation holds one gateway handler thread for the whole wait (up to the clamped timeout); the gateway has no concurrency cap yet, so a burst of long calculations competes with hosted saves and reads in the same process.
- Direct service callers of `run_arcrho_tri` outside the `/arcrho/*` routes (Result Selection source materialization, calculated-dataset input recursion when the outer run is local) still perform the cache validation, sidecar write, dependent enqueue, and index refresh over the mapped drive; only their exchanges are hosted, and without the old visibility wait a later read of that CSV over the share can meet the redirector's cached "not found". Such a run happens only in a server process; a Client PC never runs the route itself. `GET /dataset/{id}` is the `dataset_grid_load` read, answered on the server host for a handle a hosted run registered there.
- A hosted `dataset_run` holds `reserving_class_io_lock` inside the Gateway process, so concurrent runs from different Client PCs against one reserving class serialize there — stricter than the per-process lock each client held before, and intended.
- A gateway timeout leaves the request file in the server's `requests` root until the Engine claims it or the Orchestrator's five-minute garbage collection removes it, exactly as a client-published timeout does today.
