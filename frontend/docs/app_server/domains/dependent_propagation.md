# App Server Domain: dependent_propagation

## Purpose
<!-- MANUAL:BEGIN -->
Engine-hosted dependent propagation job domain: saves write only the saved object, then enqueue one durable `ArcRhoRefreshDependents` job that ArcRho Engine executes on the server host.
<!-- MANUAL:END -->

## External Interfaces
<!-- MANUAL:BEGIN -->
- Client propagation operations require Gateway: `propagation_gateway_client` delegates to the canonical workspace read/mutation registries with fallback disabled. Queue publication, job status, Engine heartbeat, and class/project preflight/busy probes execute on server-local disk. Disabled, unreachable, or outdated Gateway capabilities refuse these operations with 503 rather than accessing SMB; an unconfirmed submitted mutation returns 504 without local retry. Existing service refusals retain their HTTP status codes. Hosted-save progress uses HTTP only on clients and returns `unknown` when unavailable. Unrelated hosted-save legacy queue transport remains outside this migration; its preflight now requires Gateway too.
- Propagation submissions carry a client-generated request ID. The server serializes publication within its process and returns an existing queued, processing, or terminal status for a repeated ID instead of overwriting status or publishing another job. Server processes bypass Gateway routing, retaining the canonical queue, heartbeat, lease, and inline Engine walk behavior. These changes preserve forced downstream recalculation and content-based review decisions.
- Canonical contract module `python-api/src/arcrho_dependent_propagation_contract.py` owns the request/status schemas, `requests/dependent_propagation/` folder layout, reserving-class lease (5 s heartbeat, 300 s stale takeover), the status-heartbeat/staleness parameters (5 s republish, 45 s processing stale, 180 s queued stale), the live-Engine heartbeat preflight (fresh `runtime/instances/arcrho_engine/*.json` mtime within 60 s), and the `find_reserving_class_propagation_hold` write-hold probe (one lock-file stat plus a scan of the normally empty queued-requests folder).
- Engine worker `server-components/src/arcrho_engine/dependent_propagation.py` claims the reserving-class lease, drains and merges queued requests for the same class (`merged_into` statuses), runs the canonical `calculated_dataset_service.recalculate_dependents` walk with one progress call per refreshed object (the object's domain as the stage), republishes the current `processing` status (primary and merged ids) every 5 s so remote pollers can tell a live slow walk from a dead worker, and retains the request file until a validated terminal status exists.
- Every eligible dataset or method Save forces the complete downstream refresh, even when its values, source snapshots, or publication revision are unchanged. DFM, Result Selection, Berquist Sherman, Bornhuetter Ferguson, Cape Cod, Bootstrap, calculated outputs, and linked inputs recalculate and republish through their canonical services. Every visited output updates its timestamp, user, and audit metadata; each downstream method preserves green when its meaningful method JSON and every published CSV are unchanged. A changed method snapshot, setting, or cached value turns green to Needs Review; existing Needs Review stays yellow. `method_review_service.refreshed_status` compares the proposed files before the atomic commit, ignoring timestamp/user/audit fields, JSON/CSV numeric formatting, and floating-point noise (numbers within 1e-9 count as equal). The explicitly saved method acknowledges its own review. Refreshed linked inputs feed their downstream methods in the same walk. One pass refreshes every object the save reaches exactly once, in dependency order: `dependent_walk_service.ordered_closure` works out the whole closure and its order up front and `run_pass` hands each node to its domain's `refresh_output` with the precedents already refreshed, so an object several paths reach is no longer rewritten once per path (`docs/plans/completed/ordered_dependent_walk.md`; the traced save that started it rewrote 26 objects 54 times). A link cycle is broken by refreshing its first-seen side once. The pass reports one progress call per object — the object's domain as the stage, the object's name as the label — so the save popup's live rows keep naming the object being refreshed and counting it against the walk's total, and the hosted-save log's stage timing keeps working without a client change. Failed calculations preserve their last valid publications, block their dependent branches, and report the failure; independent branches continue. Excel read warnings retain the documented last-value behavior and remain visible to the user.
- Every save flow (DFM, Result Selection, Bornhuetter Ferguson, Cape Cod, Bootstrap, dataset sidecar/grid saves, runtime cache writes, dataset-type formula changes) preflights `require_reserving_class_writable(project, reserving_class)` before writing anything: no live Engine refuses the save with 503, and an active hold on the class (fresh lease heartbeat or a young queued request without terminal status) refuses it with 423 so one user's walk cannot race another user's edits in the same class. Unsaved work stays in the editor either way. The Excel workbook retarget (itself the `excel_link_retarget` hosted-save kind) preflights once and wraps its nested per-file saves in `suspended_reserving_class_hold_check()` so its own first enqueue does not refuse the rest, and in `deferred_save_propagation(project, class)` so those saves' roots are collected — `enqueue_save_propagation` answers `{status: "deferred"}` for that class — and walked once by the operation's `flush()` after the context exits (inline on the Engine, one queued job elsewhere); the coalescing merge remains the backstop for saves the non-atomic gate lets through together.
- Saves are Engine-hosted (`engine_hosted_save_service` client-side, `arcrho_engine/save_jobs.py` engine-side, contract `arcrho_engine_save_contract`): a Client PC sends the save to the Gateway (`hosted_save_http_client`), which preflights, publishes the request file as the queued state on server-local disk and polls to a terminal status; no client code writes a request file (step 19 of [client_smb_retirement.md](../../../../docs/plans/client_smb_retirement.md)). The Engine claims by delete, holds the reserving-class lease, runs the canonical service save with the walk inline, and embeds the full response in its terminal success status. It also writes the legacy result file so an older client paired with a current Engine still works; a current client falls back to that file only when an older Engine omits the inline response. At the 503 deadline, the Gateway retracts a request only while its request file still exists; a request already removed by delete-to-claim gets the full processing timeout. `trackSavePropagation` resolves a `status: "completed"` payload immediately (no polling); the saving window then shows a notice listing `propagation.review_flagged_datasets` — the method outputs this walk turned from OK to Needs Review, recorded by `method_review_service.refreshed_status` into the `review_flag_collector` the pass opens, so every flip in the walk is named — one clickable name per row until the user dismisses it, and shows nothing when that list is empty (`propagation.refreshed_datasets` keeps naming everything the pass rewrote and `propagation.reachable_dataset_count` says how many objects it set out to refresh, which is what the hosted-save log records); a clicked row asks Project Instance to open that dependent's method or dataset page. No save closes its window. Only refresh/patch flows still enqueue `ArcRhoRefreshDependents` jobs and poll them. Running inline is decided once, inside `enqueue_save_propagation`, so it covers every save path rather than only the callers that happen to use `enqueue_marked_save_propagation`; `enqueue_marked_save_propagation` delegates without pre-marking: review status is decided during each successful publication, not at queue submission or claim. Queued propagation submission and status polling now use Gateway rather than client SMB, so Windows network-drive cache delays no longer affect those checks. Project Instance polls `GET /dependent_propagation/reserving_class_busy` (~5 s) to quietly pause class-mutating actions while the class is held; there is no banner above the dataset table.
- Every hosted save and plan may instead use the no-IT Gateway configured by `%APPDATA%\ArcRho\arcrho_gateway.json`. If that local file is absent, ArcRho startup reads the shared Gateway `client_url`, probes it, and enrolls the current Windows login through a lock-protected atomic registry update; Server Connection changes retry the same process. Existing local files, including `enabled: false`, are authoritative. A failed pre-enrollment check leaves SMB selected because no HTTP request was submitted. Once enrolled, the local app server sends the same `ArcRhoHostedSave` payload over HMAC-authenticated HTTP; the machine-wide Gateway performs preflight, request publication, status observation, and cleanup on server-local disk. It persists the receipt before publication, so same-ID retries return the stored outcome and conflicting content returns 409. There is no automatic HTTP-to-SMB fallback after enrollment. Plain HTTP does not encrypt dataset or method content and is for controlled performance testing only. The supported kinds are derived from the canonical `SAVE_JOB_KINDS` registry, so every save procedure is covered; a client keeps a kind on SMB only while a deployed Gateway is old enough not to advertise it.
- Successful dependent-protocol path safety checks are cached in-process for 30 s by normalized workspace root. A workspace-root change uses a different cache key, while an inaccessible root or failed path validation invalidates that root immediately. Only successful checks enter the cache; heartbeat and reserving-class hold checks still run for every save.
- Each hosted save or plan appends one structured client-side timing record to `%LOCALAPPDATA%\ArcRho\logs\client_save_latency.jsonl` (`Arcode` replaces `ArcRho` in Arcode mode). The record identifies `transport` as `smb` or `http_gateway`; Gateway records include capability time, HTTP round-trip time, attempts, and `result_source: http_gateway`, while SMB records retain detailed share timings and cleanup correlation. Payloads and method data are never logged, and logging remains best-effort.
- Saves are one-step from the UI: hitting Save commits directly, with no dependent-update preview or confirmation dialog (the two-step plan/confirm flow was removed 2026-08-14; unsaved work still stays in the editor on any refusal). The server-side plan machinery remains in place but currently has no UI caller: every save endpoint keeps its sibling `<save path>/plan` (`Mode: "plan"` in the same hosted-save contract) that runs `save_plan_service.build_save_plan` on the Engine — it resolves the save's propagation roots through `save_propagation_roots` in the module that owns the save, unions the sidecar `Dependents` closure with the dataset-type formula closure, answers with the reachable objects plus a `fingerprint` of everything it read, writes nothing, and takes no reserving-class lease. A commit carrying `plan_fingerprint` still gets the under-lease recheck and a 409 (`SAVE_PLAN_STALE_MESSAGE`) when the class moved; a commit without one (all current UI saves) skips the recheck.
- Both Engine-executed flows act as the user who submitted them, because Engine instances run under their own service profiles and any instance may claim any request. A hosted save carries `UserName` (the submitter's Windows login) plus `UserDisplayName` (that login already resolved by the submitting app server against the workspace username index); a propagation request carries `UserName` only and the Engine resolves it. Both bind `user_identity_service.acting_identity(...)` around the work, so the sidecars written by the save and by the walk — and the `index.json` rows projected from them — name the person who made the edit. `UserDisplayName` is an additive field: a request without it still identifies its user by login. See the user_identity domain.
- Server-host in-process producers (ResQ migration, public Python API) keep walking in-process but hold the same reserving-class lease.
- Because the job is the sole propagation writer, the dataset open fast path trusts sidecar status + index folder signature (see the arcrho domain), and open windows watch their object for job or other-user rewrites through the object_change_watch domain's stat-only fingerprint endpoint.
<!-- MANUAL:END -->

## Data/State/Caches
<!-- MANUAL:BEGIN -->
- Two lease scopes share the `locks` folder. A reserving-class lease is keyed by project + class; a project-scope lease (`project-<digest>.lock`) is keyed by project alone and is taken by a job that rewrites what every class derives from -- currently the dataset-type change job. While a project-scope lease is fresh, `find_reserving_class_propagation_hold` answers `{"reason": "project"}` for every class of that project, until the job narrows it: `narrow_project_scope_lease` rewrites the lease file with a `classes` list (owner token and heartbeat unchanged), after which the per-class probe answers `project` only for the listed classes and reads the lease payload to find out -- one extra read, paid only while a project lock is fresh. `find_project_scope_propagation_hold` ignores the list: the job is still running, so another project-scope job still may not start.
- Both are answered by one directory listing rather than one stat per question, because a preflight on a mapped drive pays per operation. `find_any_reserving_class_propagation_hold` uses the same listing to answer the whole-project question a project-scope job must ask before it starts, and names the class it found.
- The project-scope lease is recovered far later than a class lease (`PROJECT_SCOPE_LEASE_STALE_SECONDS`, 900 s): the job it protects can legitimately spend longer in one stage than any single class walk takes.
- A walk reads the reserving class's existing dataset names once. `calculated_dataset_service.recalculate_dependents` opens a context-local snapshot that `_existing_dataset_keys` fills on first use and the whole pass reuses; without it each nested walk called `get_index`, whose folder-signature check saw the walk's own writes and rebuilt the whole index every time (the nested walks are gone, and the snapshot is what keeps one ordering read cheap). A walk only rewrites instances that already exist, so the set cannot change while it runs, and the final `index` stage still rebuilds `index.json` once after the walk.
- The pass also keeps one walk-scoped cache dict, handed to every `refresh_output` and reached through `dependent_walk_service.walk_cache`, so each domain keeps its own precedent cache inside it and `forget_cached` drops what a just-republished object owns. A closure read of a sidecar and the owning domain's own read of it are separate on purpose: once a precedent has been rewritten, the second read has to see the new file.
- Transient runtime files under `<server-root>/requests/dependent_propagation/{requests,statuses,locks}`; statuses follow the project-duplication retention policy (retained, no automatic pruning).
- Hosted-save requests live directly under `<server-root>/requests`; statuses and legacy compatibility results live under `<server-root>/requests/save_jobs/{statuses,results}` until the client consumes them or the Engine prunes stale artifacts.
- HTTP pilot receipts live under `<server-root>/runtime/arcrho_gateway/receipts`; terminal receipts are retained for 24 hours by default, while nonterminal receipts are preserved for recovery.
- Machine-local diagnostic records under `%LOCALAPPDATA%\ArcRho\logs\client_save_latency.jsonl`, plus at most three numbered rotated backups. These files never live in the ArcRho Server workspace.
- Save responses carry `propagation: {job_id, status: "queued"}` or `{status: "completed"}` for an inline walk, including unchanged saves; a save nested inside a `deferred_save_propagation` operation reports `{status: "deferred"}` and the operation's own response carries the flushed walk.
- Server-side walk diary at `<server-root>/runtime/logs/dependent_propagation.log`, written by the Engine worker through the shared `arcrho_engine.runtime_log` appender (UTC stamps, 1 MB rotation to `.1`, every error swallowed). The Engine is packaged `--noconsole`, so this file is the only durable account of a walk: a status file keeps just the newest progress snapshot, which means a phase that stalls otherwise leaves nothing behind but file timestamps. Each job logs its queue wait and claim (including a claim missed because the class was busy, which is otherwise indistinguishable from a slow walk), one line per stage transition carrying the elapsed time of the stage that just ended, and a terminal line with the held duration plus the per-bucket dataset names and unredacted failure reasons that the client-facing status message deliberately truncates. Timing a stage on its transition is what localizes a stall: a walk that spends 15 s in one phase names that phase instead of reporting one total. The same appender backs `hosted_saves.log` and `project_duplication.log`, so all three share one rotation and never-raises guarantee.
- A hosted save's inline walk never reaches the queue, so `hosted_saves.log` carries its own timing: the terminal line reads `success in 27.4s (walk refreshed 26 of 26 reachable: …; stages: before walk 0.1s, bornhuetter_ferguson 0.8s, dfm 2.4s, …, index 19.5s; publish 3.0s)`. The two counts are the objects the walk rewrote and the objects it set out to refresh (`propagation.reachable_dataset_count`), so a walk that stopped on a failed branch reads as `refreshed 12 of 26 reachable` rather than as a save with almost no dependents. The stage marks come from the same progress hook that feeds the client's save popup, taken ahead of its throttle; dependency order interleaves the domains, so a domain is entered as often as the order returns to it and its runs are summed into one entry per domain, in the order the domains were first entered. The last run goes to the service's return, `before walk` is the save's own commit, and `publish` is the result and terminal-status writes. A failed save reports `failed after Ns` with the same stage list, so a stall that ends in an error still names its phase.
<!-- MANUAL:END -->

## Common Change Tasks
<!-- MANUAL:BEGIN -->
1. Change the job contract: update the canonical contract module first, then the Engine worker, app-server service, UI poller, and tests together.
2. Add a propagation-triggering save flow: preflight the Engine, then `enqueue_save_propagation`. Let the method publisher compare proposed content with the current publication before committing status; never run the walk or pre-mark successful branches on a client.
3. Add a hosted-save kind: register it in `SAVE_JOB_KINDS`, give its service a `save_propagation_roots` that mirrors how the save derives its roots (the plan resolves them through that one function, so the two cannot drift), and add the `/plan` route beside the save route with one shared argument projection. The UI saves in one step and does not call the plan endpoint.
<!-- MANUAL:END -->

## Known Risks
<!-- MANUAL:BEGIN -->
- Failed jobs are not auto-retried: failed methods and blocked descendants remain Review Needed; independently successful unchanged branches can stay green. Save again or refresh to retry.
- A failed walk shows the server's reason (the completed payload's `message`, or a queued job's terminal error message) in a "Dependent updates" message box in the window that saved (user decision, 2026-09-21, replacing the 2026-08-07 "no message" rule); a status that could not be read stays quiet. `trackSavePropagation` fires `onComplete` at any terminal outcome (`result` null on failure) so the table refresh always runs after the walk finalized downstream statuses. The save popup treats the null resolution as "not clean" and leaves the window open instead of closing it.
- A plain filesystem cannot atomically fence the stale-lease takeover race; the generous thresholds make it acceptable (same residual gap as project duplication). The same non-atomicity applies to the reserving-class write hold: two saves may pass the preflight together, and the Engine's claim-time merge keeps that safe.
- The write hold is freshness-bounded on purpose: a dead worker's lease stops being renewed and the hold clears after 45 s; an abandoned queued request stops holding after 180 s. Clients never delete locks — only the Engine's stale takeover reclaims them.
- The UI poller treats a `processing` status whose signature stops moving for 45 s (or a `queued` one for 180 s) as stalled; the popup closes with the window left open.
- The plan endpoints and the commit-time fingerprint recheck are currently dormant (no UI caller sends `plan_fingerprint`); a save that races another user's change in the same class is caught by the existing `expected_revision` conflicts and the reserving-class hold, not by a reviewed plan.
