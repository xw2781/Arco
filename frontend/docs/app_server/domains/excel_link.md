# App Server Domain: excel_link

## Purpose
<!-- MANUAL:BEGIN -->
Reserving-class Excel link inventory, linked-value check, targeted value refresh, and workbook retargeting for the Project Instance Excel Link Manager.

## External Interfaces
<!-- MANUAL:BEGIN -->
- Called by the Project Instance Excel Link Manager, which runs as a nested pi-window page (`ui/project_instance/excel_links_window.html`) pinned to one reserving class. See [`docs/ui/project_instance.md`](../../ui/project_instance.md).
- Neither route touches a workbook in the calling process. Every workbook question is answered by the ArcRho Server host, because linked workbooks live on network shares and the server is the machine that must be able to open them for anything to work: a Client PC's own view of a path says nothing about that, and reading workbooks over SMB from clients is what the transport avoids.
- `/excel_links/list` is the registered `excel_link_listing` [workspace read](workspace_reads.md) (`excel_link_service.list_reserving_class_excel_links`), hosted whole. It scans the reserving class's dataset sidecars (`external_links`) and v2 DFM method JSONs (Ratios User Entry `inputs`) with bounded parallel reads, groups references by workbook path (case/separator-insensitive), reports per-workbook usage counts, and stamps `exists`/`mtime` from the host's own stat of each workbook path — so `Found` means ArcRho Server can open the workbook and `Missing` means it cannot, whatever the client sees. The same pass also stamps `created`, `modified`, and `last_modified_by` from the workbook's own `docProps/core.xml` (`excel_service.excel_workbook_properties_batch`, which stats each path and reads that small package in the same worker, so a listing over a network drive does not walk the file list twice). Those are the document's record of itself rather than the file system's, which is what makes them the workbook-side answer to the dataset table's `Created`, `Last Modified`, and `User`; a workbook that is not a readable OOXML package — a legacy `.xls`, an encrypted file — reports them blank and stays `Found`, because it is still a valid link target. Unreadable JSON files are returned in `errors` instead of being silently dropped. The same function runs locally only when no gateway offers the read (or the process is itself a server process). Each workbook's `usages` entry names one dependent object — `kind` (`dataset`/`dfm`), `name`, `link_count`, `cell_count`, `method_type`, and `status`, plus for a dataset its `dataset_type` (the DFM entry carries `""` there, because a method is addressed by its own name). `status` (`excel_link_status`) is the manager's staleness check, settled in the same pass as the stat: `needs_review` when the workbook's file time is later than the file holding that usage's linked values — the dataset's CSV under the class cache folder (`csv_file`), or the DFM's method JSON itself, whose time the folder scan already returned — by more than `NEWER_WORKBOOK_TOLERANCE_SECONDS`; `updated` otherwise; and `""` when either side cannot be stated (a workbook this host cannot open, a dataset with no data file), because an unknown must not read as current. The file times themselves are not returned. `method_type` comes from `dataset_sidecar_status_service.normalize_method_type` for a dataset — the same owner the reserving-class index reads, so the manager's Method Type column and the dataset table's cannot drift — and is `DFM` for a method usage. The manager renders one table row per usage and opens the named object from it, so the Dataset Type Name must come from the sidecar that owns it rather than being guessed client-side from the instance name.
- `/excel_links/check` is the registered `excel_link_value_check` [workspace read](workspace_reads.md) (`excel_link_service.check_reserving_class_excel_link_values`), hosted on the same host and for the same reason as the listing — it opens workbooks. It is the listing with each usage's `status` settled by the values instead of the file times: the same `_scan_reserving_class`/`_build_listing` pass runs first, then every linked cell of every workbook the class references is read in one `excel_service.excel_read_cells_batch` (`_collect_refresh_read_items` under an empty `_BookMap`, so every reference counts and each one is read from the workbook it names) and applied to the stored values exactly as a refresh would, without saving anything. One verdict per (object, workbook) usage, from `_usage_value_status`: `needs_review` when any linked cell of that workbook differs, with `changed_cell_count` saying how many; `updated` when they all match; `""` plus the first reason in `check_error` when a cell cannot be read — a missing sheet, a non-numeric value, a CSV that cannot load, a workbook this host cannot open — because an unknown must not read as current. A dataset's values are loaded at the shape its links were written against (`dataset_service.load_cached_dataset_values(..., at_linked_shape=True)`), since a link names a cell of the grid the dataset was displayed at when the link was written; a DFM's cells follow the retarget's rules (a finite result greater than zero, standalone ranges spilling into their non-anchor User Entry cells, a formula mixing Excel and dataset references reported as a per-cell error). The payload is the listing's, plus `value_check: true` and those two per-usage fields, so the client can render either verdict with the same normalizer. The listing's own file-time `status` is untouched and is still exactly what `/excel_links/list` returns, which is what the manager falls back to when the check cannot run.
- `/excel_links/refresh` is the `excel_link_refresh` hosted-save kind (`SAVE_JOB_KINDS` → `excel_link_service.refresh_reserving_class_excel_links`), with `/excel_links/refresh/plan` as the dormant plan sibling every hosted-save kind carries; the router's one `_refresh_call` projection feeds both. `targets` names the objects the user accepted from the value check's preview as `{"kind": "dataset" | "dfm", "name": ...}`, and a request naming none is refused with `400`. On Arco Engine under the reserving-class lease it preflights `require_reserving_class_writable`, scans the class once, keeps only the targeted sidecars and method JSONs (`_targeted_payloads`, matched case-insensitively on the object's own name), reads their linked cells in one deduplicated batch, and — inside `suspended_reserving_class_hold_check()` and `deferred_save_propagation()` — commits through the same canonical saves a retarget uses (`save_dataset_sidecar`, `save_dfm_method`), but only for the objects whose values actually moved: one that already matches its workbook returns `saved: false` and is written nowhere. A saved DFM's output sidecar is marked Review Needed and added to the walk roots explicitly, because a DFM save with an unchanged publication submits none. No reference is ever rewritten; a refresh moves values only. `_finish_class_operation` is the tail both kinds share — flush the deferred walk once, rebuild the reserving-class index once, and return `results`, `changed_file_count` (the files actually saved), `changed_link_count`, `refreshed_cell_count`, `failed_refresh_count`, `value_changed_file_count`, the `propagation` payload, and the refreshed inventory, so the client pays one round trip.
- `/excel_links/retarget` is the `excel_link_retarget` hosted-save kind (`SAVE_JOB_KINDS` → `excel_link_service.retarget_reserving_class_workbook`), executed on Arco Engine under the reserving-class lease like every save, over the Gateway when it advertises the kind and otherwise as a request file; `/excel_links/retarget/plan` is the dormant plan sibling every hosted-save kind carries. On the Engine the retarget first opens the picked workbook with `excel_service.excel_workbook_readable` and refuses with `400` (`ArcRho Server cannot open the selected workbook: <reason>`) when the server cannot read it — nothing is written; the window shows that verdict together with the path the user picked, since the server redacts paths from its messages. Otherwise it preflights the class hold, reads every mapped cell of every affected dataset and DFM (including other-workbook references inside affected DFM formulas) in one deduplicated openpyxl batch, and rewrites and refreshes each affected file through its canonical save — `save_dataset_sidecar` for datasets (always, even when every refreshed value equals the stored snapshot: the link changed, which is an audited change; when the CSV cannot be loaded the sidecar alone is saved and the cells are reported as failed) and `save_dfm_method` for DFMs, after which the DFM's output sidecar is marked Review Needed (`dfm_service._mark_review_needed`) because an explicit save resets it and its inputs moved without the owner looking. The nested saves run under `suspended_reserving_class_hold_check()` and `deferred_save_propagation()`, so their roots — every affected dataset plus every affected DFM's output, the latter added explicitly because a DFM save with an unchanged publication submits none — are collected and the class is walked once at the end (inline on the Engine, one queued job from a direct caller); the walk re-marks the whole reachable closure Review Needed and refreshes it, so every dependent is flagged whether or not the new workbook changed a value. Value rules mirror the client Links-tab refresh: dataset links accept any finite number, store blank cells as null, and stay per-link atomic on failures; DFM cells require a finite result greater than zero rounded to six decimals, standalone ranges spill literal values into non-anchor User Entry cells, and a formula mixing Excel and dataset references reports a per-cell error to be refreshed from the DFM Links tab. Cells that cannot be refreshed keep their stored values while the reference rewrite still persists. The response carries per-file `results`, the aggregate counts, the flush's `propagation` payload, and the refreshed inventory (resolved on the same host) so the client pays one round trip.
- `/excel_links/break` is the `excel_link_break` hosted-save kind (`SAVE_JOB_KINDS` → `excel_link_service.break_reserving_class_excel_links`), with `/excel_links/break/plan` as its dormant plan sibling; the router's one `_break_call` projection feeds both. `targets` names the manager rows the user confirmed as `{"kind": "dataset" | "dfm", "name": ..., "workbook_path": ...}` — one row is one object reading one workbook, so only that pair's references go and a second workbook the same object reads keeps its link (a blank `workbook_path` breaks every link the object holds); a request naming no object is refused with `400`. It opens no workbook at all: a break reads nothing from Excel and moves no value. Under the reserving-class lease it scans the class once, keeps only the targeted files, and — inside `suspended_reserving_class_hold_check()` and `deferred_save_propagation()` — saves each object through its canonical save: a dataset with the surviving `external_links` and no values (`_save_refreshed_dataset` with an empty refresh, so the stored CSV is untouched), a DFM with every User Entry cell reading those workbooks replaced by the number it already shows and its `display_inputs` cell cleared (`_hard_code_dfm_cells`, mirroring `hardCodeDfmUserEntryTarget` in the DFM Links tab). Because no saved number moves, a broken DFM's output is neither marked Review Needed nor added to the walk roots. The response is `_finish_class_operation`'s, plus `broken_link_count`.
- `save_propagation_roots(project, reserving, old_workbook_path, new_workbook_path, targets)` answers for all three hosted-save kinds from one function, which is what lets each live in the hosted-save registry and keeps a plan from deriving a root differently from the save it precedes. With `targets` it mirrors the refresh's and the break's roots (each targeted dataset by `dataset_type`, each targeted DFM's output through `dfm_service.save_propagation_roots`); without them it mirrors the retarget's (every dataset whose links name the old workbook, every DFM whose inputs reference it, and their outputs), and a retarget onto the already-linked workbook has no roots at all.
<!-- MANUAL:END -->

## Data/State/Caches
<!-- MANUAL:BEGIN -->
- Retargeting is never metadata-only: every affected dataset and DFM is re-saved from the new workbook, so their audit logs, `updated_at`, publications, output CSVs, and output sidecars follow the normal save rules, and every reachable method-backed dependent ends at Review Needed. Plain input datasets cannot carry Review Needed themselves (their `method_type` is `None`); their dependents are what the walk flags.
- Legacy v1 DFM method files are ignored by both listing and retarget; they surface only after their one-time v2 upgrade.
- After the walk the reserving-class `index.json` is rebuilt once more, covering the review flags stamped after the DFM saves and a queued (non-inline) walk; open Dataset windows learn about the on-disk change through the existing object-change fingerprint watch.
- The new workbook must be readable by ArcRho Server at retarget time; picking the already-linked workbook is a no-op success.
- The *listing's* `status` is a file-time comparison, not a value comparison: it says the workbook was saved after the linked values were last written, not that any linked cell changed. It is the one place in ArcRho a file time still decides anything, and only as a fallback: the value comparison is `/excel_links/check`, it is what the manager shows, and the file-time verdict is what the window drops back to when the check fails, which is why the Status tooltip always names the basis a row's verdict rests on. A Dataset or DFM window compares values too, on its own object (`validateLinks` in `ui/shared/dataset/dataset_external_links.js`, `checkDfmExcelLinkFreshness` in `ui/method_pages/dfm/ratios_summary/summary_excel_validation.js`), and never looks at a file time at all. Refreshing the links — from the manager, or from the Dataset or DFM window's Links tab — clears either, because that save rewrites both the stored values and the file the time comparison reads.
- The value check writes nothing and takes no lease: it is a read, with the fallback rule every workspace read has, so a gateway that cannot answer it means the check runs locally rather than not at all. What it costs is one batched open of every workbook the class references, so the cost follows the class's linked cells rather than the caller. The manager runs it on open, again whenever its listing poll sees the listing move, and again immediately before a refresh preview, so the preview never rests on an older comparison than the one the user is looking at.
- A refresh is value-only and object-scoped: an object whose stored values already match is not touched, so its `updated_at`, audit log, publications, and output files are untouched too — the difference from a retarget, which re-saves every affected file because the link itself changed. Only the objects actually saved become walk roots, but the walk from them still re-marks and refreshes their whole reachable closure.
<!-- MANUAL:END -->

## Common Change Tasks
<!-- MANUAL:BEGIN -->
1. Add link source kinds (other method types): extend the scan/rewrite pair and `save_propagation_roots` in `excel_link_service.py` and keep the reference syntax mirrored with `ui/shared/integrations/excel_reference.js`. A new kind is picked up by the listing, the value check, the refresh, and the retarget together, because all four read the class through `_scan_reserving_class` and the same `_collect_refresh_read_items` batch.
2. Change what a Status verdict means: `_usage_value_status` owns the check's per-usage verdict and `excel_link_status` the listing's file-time one. Both are rendered by `excelLinkStatusTooltip` in `ui/project_instance/excel_links_table.js`, which states which basis it is showing, so a change on either side has to move that text with it.
<!-- MANUAL:END -->

## Known Risks
<!-- MANUAL:BEGIN -->
- The Python reference parser must stay in sync with the canonical frontend Excel-reference syntax.
- Retargeting changes saved files that open Dataset/DFM windows may hold in memory; their change-watch alert and DFM owned-revision conflicts are the guardrails.
- The Engine's service profile must be able to reach every share that holds linked workbooks; a share only client PCs map reports `Missing` and refuses retargets, by design.
- The value check opens every referenced workbook of the class each time it runs. The client-side listing signature (`excelLinkListingSignature` in `ui/project_instance/excel_links_window.js`) is the only thing keeping the 15-second listing poll from turning that into a batched workbook read every 15 seconds; a change that widens what the signature covers widens that cost.
- A refresh's `targets` are object names, not files: two objects of the same name in the class would both be refreshed. The scan is per reserving class, where names are unique, which is what makes the case-insensitive name match safe.
