# Frontend: Shell

## Purpose
<!-- MANUAL:BEGIN -->
Shell-level tab/iframe host for all feature pages.
It owns the main desktop frame, home view, docked/floating tab layout, scoped menus, hotkeys, shell preferences, iframe message routing, and Electron host bridge coordination.
The shell keeps one active top-level tab across docked and floating tabs while preserving iframe sessions as tabs move between layouts.
The desktop shell hosts ArcBot and has no global auto-save mode; workflow and editor file saves are explicit.
The floating window minimize control docks that window back to the end of the main tab strip without activating the docked tab; focus remains on the prior docked tab unless another floating window is still present, in which case the top layered floating window becomes active.
Detailed menu, floating-window, lifecycle, and bridge behavior belongs in focused sections or source-specific docs, not this overview.
<!-- MANUAL:END -->

## External Interfaces
<!-- MANUAL:BEGIN -->
- Help → User Guide is available on every page. `user_guide.js` reads `/server_profiles.current.gateway_url` at the time of the click and opens that Gateway's `/user-guide/` in the default browser through the HTTP/HTTPS-only `open-external-url` host action. Browser mode opens a separate tab. Missing connection settings, blocked popups and host failures appear in the status bar; there is no file/share or bundled-page fallback. The Gateway serves deployed documentation from its own Server root, so later guide updates require no desktop release.
- Communicates with child iframes via `arcrho:*` postMessage events.
- The main docked tab strip keeps a stable row height and connects the active tab to the shell body through border and stacking-layer styling rather than resolution-sensitive transform offsets.
- Every docked tab draws a 14px type icon at its left edge. `tab_strip.js` emits only a `tabTypeIcon` element carrying the tab type; the drawing for that type is chosen entirely in [`ui/shell/tab-type-icons/tab_type_icons.css`](../../ui/shell/tab-type-icons/tab_type_icons.css), which masks one monochrome SVG per type over the tab's own text color so every theme is covered without a recolored copy. A tab type with no icon of its own falls back to a generic page glyph. The set can be reviewed at [`docs/ui/tab_type_icon_preview.html`](tab_type_icon_preview.html).
- Home is permanently docked as the first tab. Dragging or docking other tabs cannot place a reorder preview before Home, move Home during preview animation, or persist Home anywhere else in restored tab state.
- Whenever this window's server is not production (the default server profile), the titlebar shows a small amber badge after the app name naming it: the profile's name, or `Set at launch` while a launch override fixes the server. Its tooltip adds the Gateway address and the folder, and clicking it opens the Server tab. `ui/shell/server_badge.js` reads `GET /server_profiles` once as the shell starts, since the server changes only with a restart; the rule lives in `activeServerBadge` in `ui/server/server_model.js`. Production shows nothing.
- In Dark mode, the three main-window titlebar controls use the shared raised surface and strong border tokens, with a restrained accent hover for minimize/maximize and a danger hover for close; their SVG strokes follow the current control foreground color.
- Invokes app-server endpoints for workflow import helpers and configuration endpoints.
- Uses Electron host bridge and explicit shell commands for shutdown/clear-cache actions; ordinary document unloads and reloads do not send app shutdown.
- The desktop host consumes F5 and Ctrl+F5 as no-op shortcuts so accidental refreshes do not reload the app; Ctrl+R remains the explicit shell refresh shortcut.
- The shell routes `Ctrl+PageUp` and `Ctrl+PageDown` to the shared tab runtime in the active Dataset, DFM, Bornhuetter Ferguson, Cape Cod, Result Selection, or Project Instance iframe. This makes inner-page tab cycling available before keyboard focus enters the iframe; Project Instance forwards the command again to its active floating Dataset or method window.
- The desktop window is frameless, so the shell paints its own frame edge through `body::after` and the `--shell-frame-border` custom property. Windows 11 gets right and bottom edges only; Windows 10 gets all four (`body.win10-borders`), from the host's `windows-frame-style` answer; off Windows that answer is empty and the shell draws no frame. On Windows 10 an unpackaged launch adds `body.dev-frame` from `app-info`'s `isPackaged`, which retints that same frame to `#528bff` so a development window is unmistakable beside an installed one. It changes only the color - the frame geometry stays owned by the Windows 10 rule, and Windows 11 is untouched because its frame is the operating system's.
- Any status message carrying "Sign in to the server again" (the app server's refused or missing sign-in, from the shell or a page's `arcrho:status`) shows a `Sign in again` action beside it; it posts `POST /server_profiles/sign_in`, as the Server tab's button does, and reports the result in the same place.
- The desktop shell uses a 10px left/right workspace gutter; the menubar and status bar run flush to the desktop window border, with the status bar showing a decorative resize glyph only. It does not expose custom drag-to-resize behavior, so window resizing is left to the native Electron window frame while in-shell floating tab windows keep their own resize controls.
- The Macro and Macro Library windows capture their current dimensions when opened and do not resize with the host desktop window; their own resize handles remain the only way to change their dimensions through the shared floating-window frame.
- Clear Cache & Reload is available from the Settings menu and `Alt+Q`. It runs immediately, asks open Project Instance tabs for a current state snapshot, stores a one-shot shell restore payload in the Electron host, clears Electron cache/storage, then reloads the shell with a fresh timestamped UI URL and restores the previously active page/tab layout before normal localStorage persistence resumes. Because this command is an explicit forced reload, the Electron host temporarily overrides descendant-page `beforeunload` cancellation while navigating; open nested DFM windows therefore cannot leave the shell stuck at the reload status. File > Restart uses the same Electron cache/storage clear and restore snapshot before posting the app restart requests, so users do not need to run Clear Cache & Reload separately before restarting. If the desktop host cannot perform the cache reload, the shell reports that status and falls back to a browser reload. Project Settings iframes include the shell UI version query parameter so reloads fetch the current Project Settings HTML/module graph consistently.
- App-server startup is host-managed on preferred local port `28765` by default (`ARCRHO_PORT`/`ARCODE_PORT` override), with retry on transient launch failures; Electron verifies a per-launch `/app/health` token so it does not attach to a stale backend process that happens to be listening on the same port, clears mismatched listeners before starting its backend, writes packaged app-server stdout/stderr logs under the Electron user-data `logs` folder, and writes Electron main-process startup logs plus a visible startup-failure dialog for diagnostics. The token includes a SHA-256 profile identifier derived from the current Electron user-data path (`ARCRHO_USER_DATA_DIR` overrides that path, which is how `tools/local_server.py launch-app` runs a test app beside the normal one without reusing its backend), and sibling-backend reuse requires that profile identifier as well as the packaged artifact identity (or the project root in development). When another Windows user's ArcRho backend already owns the preferred machine-wide port, it is never reused; startup uses a free fallback port and launches a backend under the current profile instead. After the backend is ready, the host publishes the effective endpoint to the per-user `%APPDATA%\ArcRho\app_endpoint.json` (or `%APPDATA%\Arcode\app_endpoint.json`) discovery file for local integrations and removes it on clean exit when it still owns the file. This backend lifecycle logic lives in `electron/backend_lifecycle.js`, installer update checking in `electron/update_checker.js`, and shared host logging/utility helpers in `electron/host_support.js`; `electron/main.js` owns windows, IPC, and app wiring.
- After the packaged desktop shell is visible, the Electron host checks the project's GitHub Releases (`xw2781/ArcRho` by default, override with `ARCRHO_UPDATE_GITHUB_REPO`/`ARCODE_UPDATE_GITHUB_REPO`) for a newer installer asset without blocking startup. Development and other unpackaged launches skip installer update checks by default because they run from the local source tree; set `ARCRHO_ENABLE_DEV_UPDATE_CHECK=1` before launching only when intentionally testing updater behavior in dev. Unpackaged launches mark the splash page and About dialog display version with a trailing `+`, such as `1.2.7+`, so dev launches are visually distinct from installed releases; the host appends that suffix to `app.getVersion()`, whose only source is `package.json`. `ARCRHO_DISPLAY_VERSION` (or `ARCODE_DISPLAY_VERSION` in Arcode mode) overrides the displayed string when it is set, but no launcher sets it - a launcher that pinned the display version to an external release feed would keep showing that feed's version no matter what the source tree holds. The no-console dev supervisor runs npm scripts in silent/no-window mode so the npm package banner does not show stale source-tree package versions during startup. The About dialog also exposes a Check for Updates button that runs the same host check and reports when ArcRho is already current, when update checks are unavailable, when the update location is unavailable, or when a newer installer exists but is missing the required SHA-256 checksum asset, and a Release History button beside it. When the user accepts an update, the host downloads the installer asset over HTTPS to the Windows `Downloads` folder (`app.getPath("downloads")`, falling back to the Electron user-data `updates` folder - `%APPDATA%\arcrho-electron\updates` - only when that path cannot be resolved), and shows the progress outside the main window: the moment the user clicks Update now, the main window is hidden and the startup splash window is reopened as the update window (`updateHost` in `electron/main.js`, driven by `electron/update_checker.js` through the same `splash-progress` channel as startup), so the user never sits in front of a frozen main window. Its bar follows every downloaded chunk and its caption reads `Downloading <app> <version>... 64.0 MB / 256.0 MB`, refreshed once a second because the splash fades its caption on every text change; both sides stay in MB so the units cannot change mid-download. A failed download or checksum closes the update window and brings the main window back before the error box. Update checks time out quickly, require a SHA-256 checksum on the downloaded installer before launching it, and treat Update now as the one click - no second "Quit the application?" prompt follows it.
- The update prompt is an in-app window, not a native message box. The host asks the renderer for a choice by calling `window.__arcrho_show_update_dialog(payload)` and awaiting `{ choice: "update" | "later" }`; the dialog lives in `ui/shell/release_notes_dialog.js` with markup in `ui/index.html` and styling in `ui/shell/shell.css`. Its notes area is capped at `min(52vh, 460px)` and scrolls, which is why a long release no longer stretches the window past the screen and why the per-change detail bullets are kept. When the renderer cannot answer - no window, a load failure, or a page without the global - the host falls back to the previous native message box, whose notes stay truncated at 12 summary bullets with an `and N more changes` line, because a native box can neither scroll nor be given a height.
- Skipping versions does not skip their notes. The update check keeps every published release newer than the installed build up to the one it will install, so a 1.4.0 to 1.4.2 jump shows 1.4.1 as well - one collapsible section per version, newest expanded. A `mandatory: true` marker on any version in that span applies to the update. Only the winning version's `.sha256` asset is fetched, so widening the scan to 30 releases costs no extra round trips.
- One reader owns a release body for both surfaces (`releaseNoteEntries` in `electron/update_checker.js`): it keeps the `## User-Facing Changes` section and drops the section label itself, `## Internal Notes`, `## Fragment Sources`, the release title, and the `Released on` line, which is carried as a separate field instead. Markdown syntax is stripped - `### Improvements` / `### Fixes` become group labels and `- **scope**: summary` becomes a bullet. `includeNested` is the only difference between the two surfaces: the scrolling dialog takes the nested detail bullets, the native fallback does not. Note text reaches the DOM through `textContent`, never as markup.
- About > Release History opens the same window over the notes bundled with the installed build. `readLocalReleaseHistory` reads `docs/releases/*.md` from the app root - the files `build/release/release_notes.py` generates, which are packaged by `package.json`'s `files: ["**/*"]` - so the history is complete from the first release up to the installed version, needs no network, and needs nothing persisted: each upgrade ships a newer set. A build without that folder reports it rather than showing an empty window.
- Downloaded installers do not accumulate. The download never overwrites an existing file: a name already in `Downloads` takes an ` (1)`, ` (2)`, ... suffix, so cleanup can only ever delete a file ArcRho itself wrote. A failed download removes its own `.part` file, and a failed checksum verification removes the downloaded installer. After a successful verification the host first closes the app completely - watchers, ArcBot, and the backend, which is stopped outright and its exit confirmed by `stopBackendForUpdate` in `electron/backend_lifecycle.js` (the shared-backend rule that keeps a backend alive for other windows does not apply, since every window closes for the update) - then launches setup with `--updated`, records the installer path in `pending_update_cleanup.json` under Electron user data, and ends the process with `app.exit`. The order matters: setup replaces the files the backend runs from, and a backend still alive when setup started could only be reported as "cannot be closed". The ordinary quit path holds `before-quit` with `preventDefault` until the same cleanup has finished, because Electron does not wait for an async handler and the shutdown used to race the exit. The next launch deletes that installer once the main window is visible, retries once about 20 seconds later while setup still holds the file locked, and otherwise leaves the marker for the following launch. The same startup pass clears installers and partial downloads left behind in the former `%APPDATA%\arcrho-electron\updates` folder and removes that folder.
- Starting the downloaded installer is treated as its own failure-prone step. The host closes its own file handles first - the download stream is awaited to `close` rather than to the `end()` callback, and the SHA-256 read resolves on `close` - because Windows refuses to start an executable another handle still holds. A launch that fails with `EBUSY`, `ETXTBSY`, `EACCES`, or `EPERM` is retried at 0.4s, 1.2s, 2.5s, and 5s, since whatever inspects a freshly written executable (Defender's real-time scan above all) releases it on its own; a still-failing launch falls back to `shell.openPath`. `spawn` reports some failures synchronously and others as an `error` event, so the launch resolves on the child's own `spawn`/`error` outcome - an unhandled `error` event would otherwise take the main process down instead of reaching the error dialog. When every attempt fails, the dialog names the verified installer path so the user can run it manually, and no cleanup marker is recorded, so that file survives the next launch.
- Home has no left navigation panel. A compact welcome panel at the top of the Launch Center contains the existing brand identity, a welcome message, and the low-contrast circular SVG initial mark. The brand resolves the current Windows login through the app server and shows its case-insensitive `full_name` mapping from the workspace-global `config/username_index.json`; an unmapped login remains visible unchanged. If the identity endpoint is unavailable, Electron sessions fall back to the host-provided login name and plain browser sessions keep the default ArcRho identity.
- The Launch Center owns its own vertical scrollbar and never scrolls horizontally; the card grid reflows to the available width instead. Every element between `.home` and `.homeLaunchPage` carries a definite height so that scroll container resolves - with an auto-height ancestor the page simply grew past the viewport and was clipped with no way to reach the rest.
- The shell chrome keeps a fixed height regardless of what the active page holds. `body` is a flex column that never scrolls, so rows adding up to more than the window are resolved by shrinking whatever may shrink: the titlebar is therefore `flex: 0 0 var(--titlebar-h)` rather than a bare height, and `.content` is `flex: 1 1 0` rather than `1 1 auto` so it takes what the fixed rows leave instead of asking for its own content height. Both are required - a content row sized from a tall page pushed the shrinkable titlebar, so the titlebar changed height when the active tab changed.
- Full screen gives the page the whole screen. Entering it - `F11`, or any other route the window takes - marks `body` with `app-fullscreen`, which lifts the titlebar, the menubar and the tab strip out of the flex column onto fixed positions above the page and slides them off the top edge, so the active page starts at the first pixel. Moving the pointer to within five pixels of the top brings all three rows back over the page (`chrome-revealed`), and they slide away again shortly after the pointer leaves them; an open menu, a tab being dragged, a pointer still on the rows, or keyboard focus inside them defers that. The rows take the opaque workspace surface while they float, because their docked translucency would show the page through them, and the tab strip carries the workspace gutter as padding since it no longer sits inside the body's. Nothing is pinned over the top edge to catch the pointer - a strip there would swallow clicks aimed at the top pixels of a tab - so `ui/shell/fullscreen_chrome.js` reads the pointer position instead. The window is frameless, so only the Electron host knows the window's full-screen state: it sends `arcrho:fullscreen-change` on the window's own `enter-full-screen`/`leave-full-screen` events, each carrying the state that event names rather than `isFullScreen()`, which still reports the state the window is leaving while they fire. The shell also asks `isFullscreen()` once when the host bridge becomes ready. `--titlebar-h`, `--menubar-h` and `--topbar-h` own the three row heights for both the docked layout and the slide distance.
- Home presents its launch groups directly below the welcome panel without a separate Launch Center heading. General is the first group, followed by the workspace-specific groups. Group labels use a larger title-case treatment, and consecutive groups are separated by low-opacity divider lines derived from the active theme's neutral border color. Hovering any launch or shortcut card keeps the existing lift and adds a soft ArcRho-blue glow; both themes own their glow through `--ar-home-card-glow`, because the tint that reads on the pale canvas disappears against the dark one.
- The Home Launch Center no longer has a `Datasets & Methods` group. Datasets, DFM, Bornhuetter Ferguson, Cape Cod, and Result Selection are opened from Project Instance instead, so Home's fixed groups are `General` and `Automation`. The shell still owns the `openDatasetTab`, `openDFMTab`, `openBornhuetterFergusonTab`, `openCapeCodTab`, and `openResultSelectionTab` actions for Project Instance, the tab strip `+` menu, browsing-history restore, and UI automation. The `File Browser` card opens a new `file_explorer` tab, which defaults to the `File Browser` title and adopts the selected folder's configured nickname, or its folder name when no nickname exists. Home group labels use title case rather than all-uppercase styling.
- Below the fixed groups, users build their own Home from custom groups of shortcut cards. `General` and `Automation` stay fixed and cannot be renamed, reordered, or hidden. A card is created from a tab that is already open: the Add card dialog lists every open tab the shell can reopen, showing its type and restore summary, and the card stores that tab's normalized restore descriptor. Clicking a card opens it through `openShellActivityHistoryEntry`, so each page keeps its own rule - Project Instance focuses the tab for the same project, Project Explorer, Browsing History, and the ArcBot guide stay single-tab, and Dataset, DFM, and Workflow open a new tab each time. Groups are arranged through a right-click or `...` menu (add card, rename, move up/down, delete). The space below the last Home group is a hover region: moving the pointer over it reveals a centered `+ New group` frame under the divider, and only clicking inside that frame opens the naming prompt; right-clicking there still opens an `Add new group` action. A card's own menu carries only `Rename card...` and a red `Delete`: placement is the drag's job, so the menu holds nothing a drag already does. Deleting a group asks for confirmation through the shared app confirm dialog; deleting a single card does not. `ui/shell/home_shortcuts.js` owns the document and its persistence, `ui/shell/home_shortcuts_view.js` owns rendering and interaction, and `ui/shell/home_card_icons.js` is the single icon source for built-in and custom cards alike.
- Custom group layout follows the fixed groups: the first custom group carries the same divider that separates `General` from `Automation`, group titles ellipsize instead of pushing their hover-only `...` button out of place, and a long card name ellipsizes clear of the card's options button. Every custom group ends with a dashed `Add card` tile that opens the same Add card dialog as the group menu, so an empty group and a full one both show one visible way to pin another tab. The tile, the group `...` button, and the card options button are frameless and take a quiet tinted hover instead of a border.
- A custom card opens on a mouse release within 200ms. Pressing and holding it for half a second instead starts reordering; after the 200ms click threshold, a bar fills along the bottom edge during the remaining 300ms, and moving the pointer more than a few pixels cancels it. The shared `Hold to drag and reorder` tooltip dismisses as soon as the card is pressed, so it cannot remain over the page opened by that card. Releasing between the click and drag thresholds also cancels the gesture without opening the card. The drag never reorders the DOM: card slots are frozen when the drag starts, the held card follows the pointer, the cards it passes are moved between those slots by transform, and the group's cards are inert for the duration so hover cannot add motion the preview did not ask for. A card can also be carried into another custom group: every custom group is measured when the drag starts, the group under the pointer becomes the drop target and is tinted, and its cards open a gap at the drop slot. A group's last slot is its `Add card` tile - which is why the tile is hidden but not removed for the duration - so a card can land after the last card as well as between two. A group already holding `MAX_CARDS_PER_GROUP` cards is never offered as a target. Releasing settles the card into the previewed slot; `Escape` cancels the drag and restores the saved order.
- `placeCard` is the one placement rule behind all of this: it lifts a card out of its group and puts it at an absolute slot in any group, its own included. Because dragging is the only way a card is placed, there is no step-wise `moveCard`/`moveCardToGroup` pair beside it defining the same move a second time. Within one group the last slot is `length - 1` because the card is already counted; arriving in another group adds one, so its last slot is `length`.
- Home shortcut cards persist per Windows user per PC in the `homeShortcuts` section of `%APPDATA%\ArcRho\local_project_prefs.json` through the existing `/local-project/preferences` routes, so they survive Clear Cache & Reload. A failed save is reported on the status bar and the previous layout is restored rather than left half-applied.
- `File Browser` is multi-instance and folder-keyed. `openFileExplorerTab` focuses an existing `file_explorer` tab only when the request names a folder that tab is already showing; a request with no folder, or with `forceNew`, always creates another instance. Each tab's folder is tracked from the page's `arcrho:file-explorer-path-changed` message, persisted in shell state, and carried in its restore descriptor, so two workspace tabs can sit on different folders and both come back after a restart. Folder watches are keyed per `watchId` and the visibility broadcast covers every instance, so instances do not interfere with each other.
- The shell owns File Explorer tab lifecycle only. Feature UI and behavior live in the isolated `ui/file_explorer/` iframe, with explicit `arcrho:file-explorer-visibility` messages used to pause background or minimized folder watches and refresh the active folder when the page becomes visible again.
- File Explorer and Arcode share the canonical `ui/shared/file-icons/` resolver, mapping, and SVG assets. File Explorer metadata fields remain opt-in so older Arcode listing consumers keep their original payload shape.
- Uses Electron host bridge for Server Connection folder browsing and first-time `ArcRho Server` drive detection, plus desktop folder watches for Arcode file explorer refreshes and Project Instance selected-path `index.json` update prompts.
- ArcBot widget markup, styling, panel behavior, model/session controls, attachments, and context UI live in the shared `ui/ai-assistant/` package; the ArcRho shell uses the `arcrho` adapter so launcher storage keys, active-tab context messages, and DFM edit approval stay ArcRho-scoped.
- ArcBot-specific Electron IPC handlers, request/client state, Codex/Claude command integration, prompt assembly, edit staging, and lifecycle cleanup live in `electron/arcbot_host.js`; `electron/main.js` registers that host module while keeping app startup, windows, menus, backend control, updates, and general shell bridge handlers separate.
- Uses Electron host bridge for desktop-only ArcBot Codex CLI status, install, login, persisted chat sessions, streamed activity/output events and assistant response deltas, file revision checks, per-request timing logs under `Documents\ArcRho\ArcBot\request_logs`, and warm `codex app-server` turns with fallback to one-shot `codex exec` requests. The host keeps one long-lived app-server process because the official Codex SDK wraps the same transport, while each request starts a fresh ephemeral thread and hydrates it once from the bounded persisted chat transcript so prior messages are not duplicated. Warm turns route notifications by thread/turn, support an optional final-response JSON Schema, batch streamed normal-chat deltas, and fail promptly when the app-server disconnects. Menu items use `data-table-colors`; boot supplies the canonical label. The Dataset Viewer does not boot this method-table preference.
- The docked tab and floating titlebar context menus include scripting-only actions for `Open File Location` and `Copy File Path`; scripting title updates include the tab instance id and current file path so background scripting tabs update their own tab title/path rather than the active tab. Holding the pointer still over a saved scripting tab or floating scripting titlebar for two seconds shows the full file path in the shell styled tooltip; moving the pointer hides or cancels it.
- In the desktop app, dragging files from File Explorer over the shell or an open feature iframe shows a shell-owned drop overlay. Dropping `.ipynb`, `.arcnb`, or `.py` files opens each scripting file in Arcode. A panel that reads a dropped file itself marks its root element with `data-file-drop-zone`; the shell's drag and drop handlers return without preventing the default or showing the overlay when the event starts inside one, so the panel receives the drop. `ui/shared/components/settings_file/settings_file.js` sets that attribute for every panel that takes a settings file, which today is the project instance path tree and its dataset panel.
- Arcode owns scripting recent files and notebook/code-editor tab behavior; the ArcRho shell no longer creates new in-shell scripting tabs.
- Before closing the active top-level tab for `Ctrl+W`/close-tab shortcuts, the shell lets the active iframe consume the shortcut through `window.__arcrho_consume_close_shortcut`; dirty Dataset and DFM tabs use this to show their in-page discard confirmation first, and project instance tabs use it to close their top floating dataset window first.
- OS-level detached tab pop-out windows are not supported; floating tabs stay inside the main shell and reuse the same iframe/message contracts as docked tabs.

## Data/State/Caches
<!-- MANUAL:BEGIN -->
- Persists tab state, docked/floating layout, floating window position/size/z-order, zoom, and toggles in `localStorage`; Clear Cache & Reload preserves the current shell tab snapshot through the Electron host because the action intentionally clears browser storage.
- Persists File Explorer favorites in `%APPDATA%\ArcRho\prefs\home_folders.json` as the normalized versioned document `{ "version": 1, "folders": [{ "path": "...", "nickname": "..." }] }`. The Electron file is authoritative and written atomically so favorites survive Clear Cache & Reload; `arcrho_home_folder_preferences_v1` local storage is only a browser fallback and first-run migration source.
- Persists the normalized frontend color theme (`light` or `dark`) as the local OS user's authoritative `color_theme` preference in `%APPDATA%\ArcRho\prefs\main_window_prefs.json`. The shared `arcrho_color_theme` local-storage value is a renderer cache that is seeded from the user preference at startup; an existing cache is migrated into the preference file when that field is first introduced. Clear Cache & Reload may clear browser storage, but it preserves the user preference and the derived native-window background cache, passes the stored theme into the reload URL for correct first paint, and restores the renderer cache from Electron.
- Persists the table style (`revolutionary` or `classic`) the same way, as `table_style` in the same file, with `arcrho_table_style` as its renderer cache; the host passes it to the main window as `tableStyle` in the URL and keeps it through Clear Cache & Reload. With no saved value the app opens in Revolutionary.
- Persists project instance tab identity using the selected project name plus project folder/table-path metadata.
- Persists dataset browsing history entries (latest 100, one per dataset per day) via `browsing_history.js`.
- Persists the latest 60 restore-capable page entries (one per page per day) under `shellActivityHistory.entries` in `%APPDATA%\ArcRho\local_project_prefs.json`. Project Instance entries also persist selected path, nested floating Dataset/DFM window names, hidden/active/maximized/dirty flags, DFM subtab, and restore rectangles. Successfully opened File Browser paths retain their own local-user browser history (latest 100, one per folder per day) under `arcrho_workspace_history_v1`.
- Persists the ArcBot launcher icon visibility and position in `localStorage`.
- Persists ArcBot chat sessions as local JSON under Electron user data, including messages, activity, mode, archived state, latest active-tab context summary, and estimated context usage; ArcBot writes shared exchange JSON/CSV copies under the user `Documents\ArcRho\ArcBot\workspace` folder while keeping per-request edit metadata under `Documents\ArcRho\ArcBot\sessions`. There are no backups or edit manifests: a later `revert latest` request asks the page that took the edit to undo it, which works only while that page is open and the edit is still its latest change.
- ArcBot panel resizing clamps saved and live widths to a 420px minimum that keeps the composer controls visible without clipping, and each app session's first ArcBot panel open starts at that minimum width while preserving the saved height. Resizing the main app window repositions the open ArcBot panel back into view without changing the panel's current width or height.
- The ArcBot model selector obtains its visible OpenAI catalog and supported reasoning efforts from the bundled Codex app-server `model/list` contract instead of a hardcoded list. New chats use the runtime contract's preferred default (GPT-6.1-Sol at Medium) while Codex advertises it, otherwise an advertised and verified GPT-5.6-or-newer default, with a newer Codex default taking precedence automatically. A stale CLI catalog that lacks GPT-5.6 triggers Repair; ArcBot never inserts or auto-saves an unadvertised model, and a temporary discovery failure blocks sends until retry or Repair verifies the catalog. Safe model slugs saved by older chats remain visible as unavailable rather than being silently replaced. Anthropic choices are discovered from the Anthropic Models API with the signed-in Claude token (newest Fable, Opus, Sonnet, and Haiku; Sonnet is the Claude default) and fall back to Claude Fable 5.1, Opus 5.5, Sonnet 5.5, and Haiku 4.5. Both discovered lists are re-read after six hours. The reasoning/thinking selector shows only the selected model's reported capabilities (including Ultra when supported), and the legacy Codex default inherits those capabilities before send. Both `model` and `reasoningEffort` remain session-persisted and are forwarded through `codexAssistantSend`; switching providers rechecks the matching credentials.
- Claude requests in the Electron host are authenticated using the OAuth access token in the active ArcBot Claude account's `.credentials.json` (`~/.claude/.credentials.json` for Primary) written by the Claude CLI (`claude auth login`); no separate API key is required. The `codex-assistant-status` IPC now returns `claudeAuthenticated` alongside the existing Codex fields, and `codex-assistant-login` accepts `{ provider: "anthropic" | "openai" }` for the active account or `{ accountId }` for a named one. The `codex-assistant-accounts-list`, `-account-create`, `-account-activate`, `-account-logout`, and `-account-remove` IPCs manage ArcBot accounts (see [ai_assistant.md](ai_assistant.md)). Claude messages are sent to the Anthropic Messages API (`/v1/messages`) over HTTPS with SSE streaming; edit sessions are skipped for Claude models (responses are conversational only).
- Dirty-state messages from workflow, DFM, and scripting tabs update the shared tab dirty indicator for both docked tabs and floating tab titlebars.

## Common Change Tasks
<!-- MANUAL:BEGIN -->
1. Add a new tab type: update `tab_actions.js` (opener, `RESTORABLE_ACTIVITY_TYPES`, history restore), `iframe_host.js`, the payload-free type list in `shell_activity_history.js` when the tab carries no state, the Home card and its icon kind in `home_card_icons.js`, relevant menu/hotkey dispatch modules, and any state persistence in `shell_state.js`; add the tab icon by dropping `ui/shell/tab-type-icons/<type>.svg` beside its siblings and adding the matching rule to `tab_type_icons.css`, or leave both out and accept the fallback glyph.
2. Add shell menu action: wire menu item + action handler in `shell_menus.js` and hotkey mapping in `shell_hotkeys.js`; for `Edit`/`View` items, always set `data-page-scopes` (`*` for global visibility) because those dropdowns require explicit scope declarations.
3. Change tab layout behavior: update `tab_strip.js`, `floating_tabs.js`, `shell_content.js`, active-tab dispatch in `tab_actions.js`, localStorage migration in `shell_state.js`, and close/dirty-state flows together.
4. Change theme behavior: keep preference normalization and messaging in `ui/shared/services/color_theme.js`, keep the Light baseline in its shared theme stylesheet and the Revolutionary table style in `revolutionary.css`, keep Dark-only deviations in `dark.css`, and preserve the `arcrho:set-color-theme` relay for existing and newly loaded iframe contexts.
5. Change File Explorer behavior: keep favorite normalization, path rules, metadata formatting, filtering, and sorting in `ui/file_explorer/file_explorer_model.js`; keep DOM interaction in `ui/file_explorer/file_explorer.js`; and preserve the shared Electron folder-listing, watcher, file-opening, and file-icon contracts used by Arcode.

## Known Risks
<!-- MANUAL:BEGIN -->
- DOM replacement in shell can invalidate iframe references.
- Unsaved-state handling must stay consistent for close/close-all flows.
- Floating/docking must reposition existing iframes without recreating or reparenting them, or feature pages can lose in-memory state.
- Active-tab styling and menu dispatch must stay single-source through `state.activeId` so docked background content does not behave as active while a floating window is focused.
- Host/app-server startup races can surface as blank shell or startup timeout if lifecycle flags/process teardown are not coordinated.
- Offline, slow, or inaccessible GitHub Releases API/asset requests must not block startup; failures should remain a skipped update check.
