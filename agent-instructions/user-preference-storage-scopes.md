# User Preference Storage Scopes

Before adding or moving an app preference, classify it into exactly one of these scopes and use the canonical path builders instead of hardcoding a drive, server root, project folder, or Windows login. A preference that belongs to the user and means the same thing on every PC is a **user preference** (scope 2); only what is tied to one PC stays local (scope 1):

1. **This-PC preference:** State that only makes sense on the current PC belongs under `%APPDATA%\Arco`: the server connection and Gateway sign-in (`workspace_paths.json`, `arcrho_gateway.json`), the main-window size, anything that is a path on this PC (`prefs\home_folders.json`, `prefs\recent_settings_files.json`, `prefs\scripting_notebook_prefs.json`), and what standalone Arcode shares with Arco (`prefs\scripting_shortcuts.json`, `prefs\arcbot_ui_settings.json`, the ArcBot accounts). The Electron profile (browser storage, host logs, downloaded updates) is `%APPDATA%\Arco\profile`; logs and scratch are `%LOCALAPPDATA%\Arco`; the user's own macros, scripts, workflows and templates are `Documents\Arco`, because they are opened through Windows file dialogs, edited in other programs and run on the PC. Standalone Arcode uses `%APPDATA%\Arcode`. The folder name `Arco` is owned by `LOCAL_APP_FOLDER_NAME` in `python-api/src/arcrho_api/config.py` (`config_dir()`, `local_data_dir()`, `documents_dir()`), mirrored for the desktop host in `frontend/electron/local_folders.js`, which also renames the folders an older app left under `ArcRho` at start. Browser `localStorage` is also this-PC state: address it by storage key, never by path, and never as the only home of something that must survive Clear Cache (`arcrho_default_window_tabs`, owned by `frontend/ui/shared/tabs/window_tab_catalog.js`, is the current key of that kind).
2. **User preference:** Settings that follow one Windows user to every PC and every project belong in the user's folder on the server, `<workspace_root>\users\<encoded-windows-login>\preferences.json`, as one named section each (`appearance`, `tableColors`, `macros`, `flightDeck`, `notesPanel`, `scripting`, `shell`). A section is read and written whole, so two windows saving different sections never erase each other. The path owner is `frontend/app_server/services/server_user_profile_service.py` (`user_folder`); a Client PC reaches it only through the Gateway (`user_preferences` / `user_preferences_update`, and the `scripting_preferences*` and `shell_preferences*` kinds), where the login is the one the request is signed with. The desktop host loads and saves a section through `/user-preferences/{section}`. The same folder holds the user's ArcBot chats (`arcbot\sessions`, `arcbot_chat_store_service.py`) and saved dashboards (`dashboards`, `dashboard_service.py`). The colour theme and table style are the one preference with a copy on the PC: the host keeps them in `%APPDATA%\Arco\prefs\main_window_prefs.json` so a start paints in the right colours before the server has been asked, adopts the server's value before the main window is built, and sends each change to the server.
3. **Project-user-specific preference:** Settings that must follow one Windows user within one ArcRho project belong at `<workspace_root>\<projects_dir>\<project>\users\<encoded-windows-login>\preferences.json`. Resolve `workspace_root` and `projects_dir` from the local `workspace_paths.json`, resolve the actual project directory through app-server config helpers, and obtain/encode the login through the shared user-identity and filename-encoding helpers. The canonical path owner is `frontend/app_server/services/project_user_preferences_service.py`; do not construct this path independently in consumers.
4. **Server-shared preference:** Settings shared by all users and projects using the configured ArcRho Server belong under `<workspace_root>\config\<preference-file>.json`. Resolve `<workspace_root>` from `%APPDATA%\Arco\workspace_paths.json`; never assume `E:\Arco Server`. The current shared dataset number-format preference is `<workspace_root>\config\dataset_number_formats.json`, canonically resolved by `frontend/app_server/config.py::get_dataset_number_formats_path()` and optionally overridden by `ARCRHO_DATASET_NUMBER_FORMATS_PATH`. The shared SQL Server import history is `<workspace_root>\config\mssql_connections.json`, canonically resolved by `frontend/app_server/config.py::get_mssql_connections_path()` with its filename and payload schema owned by `arcrho_api/source_table_contract.py`; it records server/database identifiers and a last-used timestamp only and must never hold credentials. New server-shared preferences must likewise have one canonical filename/path builder in app-server config.

**What a second app window can remember** (measured 2026-09-30 with two dev apps on one Electron profile, one theme change and one probe key written in each, both closed through the normal close path, then reopened). Two apps of one profile share one Chromium storage folder, but only the first app to start holds it; the second keeps its browser `localStorage` in memory, sees none of the first app's writes, and loses everything it writes when it closes. The first app's writes reach disk, but only under the origin of the port it ran on, so they come back only when a later app runs on that same port; an app that starts on a free port because the usual one is busy opens with empty browser storage. The colour theme and table style survive from either window anyway, because the Electron host also writes them to `%APPDATA%\Arco\prefs\main_window_prefs.json` (merged per key, last writer wins) and passes them to the page at load. Keys held only in `localStorage`, such as `arcrho_default_window_tabs` and `arcrho.notes.font-size`, are lost when set from a second app window. Nothing was moved; moving those keys to a host file is a separate plan.

This-PC preferences stay with one PC profile, user preferences follow the Windows user across PCs and projects, project-user preferences follow the project and encoded Windows user, and server-shared preferences affect every user of that configured server. Do not use local AppData for a preference that must follow the user or be shared, and do not use a server-shared file for user-specific state.
